# tvApp — ระบบดูทีวีสด

สองส่วน แยกกันชัดเจน

| โฟลเดอร์ | คืออะไร | เทคโนโลยี |
|---|---|---|
| [`backend/`](backend/) | API จัดการช่อง + ระบบ Log JSON รายวัน + JWT Auth | Hono + Node — ไม่ใช้ Express |
| [`app/`](app/) | แอปดูทีวีบน Android TV / Apple TV | Expo SDK 57 + react-native-tvos + expo-video |

> [!TIP]
> 📖 **บันทึกงานและประวัติเซสชันล่าสุด (Active Session Log):**  
> รายละเอียดเชิงลึกของการสืบสวนหาสาเหตุจริงของปัญหาช่องสดกระตุก/รีเฟรชวนลูป (Defect #8), การ Patch Native Media3 ExoPlayer, คำสั่งตรวจสอบ Backend Log และประวัติการคอมไพล์ Release APK ล่าสุด ถูกบันทึกไว้อย่างสมบูรณ์ที่ 👉 **[`current_session.md`](current_session.md)**


## เริ่มยังไง

**1. เปิด backend**

```bash
cd backend
npm install
cp .env.example .env
npm run genkey          # เอาคีย์ที่ได้ไปใส่ API_KEY ใน .env
npm run dev
```

**2. เพิ่มช่องผ่าน Postman**

Import `backend/postman_collection.json` ตั้ง `baseUrl` กับ `apiKey` แล้วยิงได้เลย

```bash
curl -X POST http://localhost:3000/api/channels \
  -H "Content-Type: application/json" -H "X-API-Key: <คีย์>" \
  -d '{"name":"ช่อง 7HD","url":"https://.../live.m3u8","group":"ฟรีทีวี"}'
```

ไม่ใส่ `logo` ก็ได้ ระบบวาด avatar ตัวอักษรแรกให้เอง

**3. ลงแอปบนทีวี**

```bash
cd app
npm install
cp .env.example .env    # แก้ EXPO_PUBLIC_API_URL ให้ชี้มาที่ backend
npm run android
```

ต้อง build เป็นแอปจริง — Expo Go ใช้ไม่ได้ เพราะ TV ต้องใช้ native fork

## Defect & Feedback Log (สรุปปัญหา สาเหตุจริง และการแก้ไขจบปัญหา)

สรุปประวัติข้อผิดพลาดและอาการที่พบระหว่างการพัฒนาบน Android TV (Toshiba TV / Emulator) พร้อมอธิบายสาเหตุเชิงลึกและวิธีแก้ไขให้จบปัญหาแบบภาษาคน

> 💡 *หมายเหตุ:* ปัญหาข้อ **8** (Live Stream Refresh Loop & Deadlock Hotfix) เป็นข้อบกพร่องล่าสุดที่มีการ Patch ละเอียดทั้ง Native Media3 และ JavaScript Layer พร้อมทั้งระบุ Runbook การตรวจสอบ Log อย่างละเอียด สามารถอ่านเอกสารประกอบฉบับเต็มได้ที่ 👉 **[`current_session.md`](current_session.md)**

### 1. อาการ: ค้างหน้า Loading Screen แล้วเด้งปิดตัวเอง (Force Close / Crash on Launch)
* **สิ่งที่เป็นปัญหา**: เปิดแอปขึ้นมาบนทีวี Toshiba โหลดหมุนสักพัก แล้วแอปเด้งดับปิดตัวเอง
* **สาเหตุจริงเชิงลึก**:
  1. ทีวี Toshiba เป็นชิปประหยัดพลังงาน แรมจำกัด และตัวถอดรหัสวิดีโอ (Hardware MediaCodec) มีโควตาจำกัด
  2. ตอนเปิดแอป โค้ดเดิมสั่งแอนิเมชันระดับสูงพร้อมโหลด Player ทันทีโดยไม่มีช่องว่างให้ระบบเตรียมตัว และไม่มี Safe Fallback ทำให้หน่วยความจำล้นและ Android สั่ง Kill Process
* **วิธีแก้ไขจบปัญหา**:
  - เปลี่ยนหน้าแรกของแอปเป็น **"หน้าหลักภาพนิ่ง (Main Channel)"** ที่โหลดเบามากใน 0ms เมื่อเปิดแอป
  - ปรับการตั้งค่า Gradle / Proguard ให้แยก 64-bit/32-bit ชัดเจน และเพิ่ม Error Boundary ดักจับ Exception ป้องกันแอปดับ

### 2. อาการ: แอปรีเฟรชตัวเองวนลูปไม่รู้จบ (Infinite Refresh Loop)
* **สิ่งที่เป็นปัญหา**: เปิดช่องวิดีโอขึ้นมาเล่นได้ 3-9 วินาที แล้วหน้าจอก็กระพริบดำ โหลดใหม่ซ้ำไปซ้ำมาตลอดเวลา
* **สาเหตุจริงเชิงลึก**:
  1. ในโค้ดเดิมมีตัวจับเวลา (Watchdog) คอยเช็คว่าถ้าไม่ได้รับ event `timeUpdate` แปลว่าสตรีมค้าง และจะสั่ง `player.replace()` เพื่อโหลดใหม่ทุก 9 วินาที
  2. แต่ `expo-video` มีค่าเริ่มต้นของ `timeUpdateEventInterval = 0` (คือ **ปิดการส่งอีเวนต์เวลา**) ส่งผลให้ Watchdog ไม่เคยได้รับอีเวนต์เลย จึงเข้าใจผิดว่าสตรีมตายตลอดเวลา และสั่ง reload วนลูปทุก 9 วินาทีไม่หยุด
* **วิธีแก้ไขจบปัญหา**:
  - ลบ Watchdog ตัวปัญหาออกอย่างถาวร
  - เปิด `timeUpdateEventInterval = 1` ให้ระบบส่งอีเวนต์เวลาจริง
  - ใช้ `useMemo` ล็อกรายการช่อง เพื่อไม่ให้ React Re-render ล้างสถานะ Player

### 3. อาการ: ดูไปสักพัก (30-60 วินาที) แล้วภาพหยุดนิ่ง ต้องสลับช่องไปมาถึงจะเล่นได้
* **สิ่งที่เป็นปัญหา**: สตรีมสดเปิดดูได้ปกติ แต่พอดูไปสัก 30 วินาทีหรือ 1 นาที ภาพจะหยุดนิ่งไปเฉยๆ รีโมตไม่ขยับ ต้องกดเปลี่ยนไปช่องอื่นแล้วกดกลับมาใหม่ถึงจะเล่นต่อได้
* **สาเหตุจริงเชิงลึก**:
  1. สตรีมสด HLS (Wowza) มีหน้าต่างสด (Live Window) สั้นมาก เพียง 30 วินาที (3 ชิ้น ชิ้นละ 10 วินาที)
  2. เมื่อเน็ตในบ้านสะดุดเพียง 1-2 วินาที หรือการถอดรหัสของทีวีช้ากว่าเวลาสตรีมสดจริง ExoPlayer จะหลุดออกจากหน้าต่าง 30 วินาทีนี้ และโยน Error: `androidx.media3.exoplayer.source.BehindLiveWindowException: Source error`
  3. ยิ่งไปกว่านั้น โค้ดเดิมดันมีบั๊กที่ trailing decoder audio event ส่งเข้ามาทีหลังแล้วไปแอบสั่ง `clearAllTimers()` ยกเลิกตัวตั้งเวลาซ่อมตัวเอง ทำให้ตัวเล่นนิ่งสนิทและไม่พยายามเชื่อมต่อใหม่
* **วิธีแก้ไขจบปัญหา**:
  - ดักจับ `BehindLiveWindowException` หรือ Source Error และสั่ง Snap กลับสู่ขอบสดปัจจุบัน (Live Edge) ทันที
  - ป้องกันไม่ให้ trailing event มาแอบยกเลิก Retry Timer ขณะที่ระบบกำลังซ่อมแซมตัวเอง

### 4. อาการ: สตรีมดูได้ปกติ อยู่ดีๆ ก็ Reload ใหม่เอง (Ghost Reload during Normal Playback)
* **สิ่งที่เป็นปัญหา**: ผู้ใช้นั่งดูทีวีอยู่เฉยๆ กำลังเล่นสดได้ดี ภาพลื่น ไม่มี error ใดๆ แต่อยู่ดีๆ หน้าจอก็ reload วิดีโอใหม่เอง
* **สาเหตุจริงเชิงลึก**:
  1. **Sidebar Focus Trigger**: เมื่อเปิดช่องเล่นไปได้ 3.2 วินาที แถบ Sidebar จะสั่งยุบตัว (Auto-collapse) พอ Sidebar ยุบตัว React Native จะทำการวาด layout ใหม่ ส่งผลให้ระบบ Android TV Native Focus ส่ง event `onFocus` ซ้ำมาที่ช่องเดิม
  2. ฟังก์ชัน `handleFocusChannel` ใน `App.js` เดิมไม่ได้ตรวจสอบว่าช่องที่โฟกัสคือช่องที่กำลังเล่นอยู่หรือไม่ จึงไปสั่ง `setPlaying` พร้อมสแตมป์เวลา `_loadEpoch: Date.now()` ใหม่ ทำให้ `Player.js` เข้าใจผิดว่าผู้ใช้กดสั่งโหลดใหม่ จึงสั่ง `player.replace()` ซ้ำ ทั้งๆ ที่ไม่ได้เปลี่ยนช่อง
  3. **False Stall Watcher**: ตัวตรวจจับค้างเดิมเช็คเพียง boolean `playing: false` แวบเดียวตอนสตรีมสลับชิ้นไฟล์ (HLS chunk transition) แล้วสั่งจับเวลา 12 วินาที พอนับครบก็สั่ง reload ทับ ทั้งๆ ที่ภาพและเสียงยังเดินหน้าอยู่ตามปกติ
* **วิธีแก้ไขจบปัญหา**:
  - ใน `Sidebar.js`: ใส่ตัวตรวจจับ `userPressedRemoteRef` — ระบบจะยอมส่งอีเวนต์เปลี่ยนช่องเฉพาะเมื่อ **ผู้ใช้กดปุ่มบนรีโมทจริงเท่านั้น** หากเป็นการโฟกัสที่เกิดจากการยุบตัวของ Sidebar หรือการจัดหน้าจอ จะไม่ส่งอีเวนต์เปลี่ยนช่องเด็ดขาด
  - ใน `App.js`: เพิ่มเงื่อนไข `if (channel.id === playingRef.current?.id) return;` ห้ามสั่ง reload หรือเปลี่ยน epoch กับช่องที่กำลังเล่นอยู่โดยเด็ดขาด
  - ใน `Player.js`: แยกแยะความ "ปกติ" กับ "ไม่ปกติ" 100% โดยตรวจสอบจาก `timeUpdate` ว่าตัวเลข `currentTime` กำลังเดินหน้าจริงหรือไม่ ตราบใดที่เวลาเดินหน้าปกติ = ห้าม reload, ห้าม retry, และห้ามแสดงหน้าต่างโหลดทับเด็ดขาด

### 5. อาการ: กระตุกติด Retry ตลอดเวลา (Infinite Retry / Stutter Loop)
* **สิ่งที่เป็นปัญหา**: พอสตรีมมีปัญหา ตัวเล่นพยายาม retry ถี่เกินไป ยิงคำสั่งซ้อนกันจนภาพกระตุก กระพริบ โหลดใหม่ไม่หยุด
* **สาเหตุจริงเชิงลึก**:
  1. ตัวนับจำนวนการลองใหม่ (`autoRetryCount`) ถูก Reset กลับเป็น 0 เร็วเกินไป (ทันทีที่ภาพเฟรมแรกขึ้น) พอสตรีมสะดุดซ้ำอีก 1 วินาทีต่อมา ระบบก็นับเป็นครั้งที่ 1 ใหม่ แล้วก็ retry ซ้ำ วนลูปไม่รู้จบ
  2. มีคำสั่ง retry หลายตัวถูกสั่งเข้ามาซ้อนกันในเวลาใกล้เคียงกัน
* **วิธีแก้ไขจบปัญหา**:
  - **Hard Cap 3 ครั้ง**: จำกัดการลองเชื่อมต่อใหม่อัตโนมัติสูงสุดแค่ 3 ครั้งพอ (ครั้งที่ 1 รอ 2.5s, ครั้งที่ 2 รอ 5s, ครั้งที่ 3 รอ 8s)
  - **หยุดสนิท (Halt)**: หากลองครบ 3 ครั้งแล้วยังไม่สำเร็จ ระบบจะ "หยุดนิ่งทันที" ไม่วนลูป ไม่กระตุก ไม่รบกวนทีวี แล้วแสดงหน้าจอแจ้งเตือนพร้อมปุ่ม **"ลองใหม่"** ให้ผู้ใช้เป็นคนกดรีโมทเองเมื่อสัญญาณพร้อม
  - **Cooldown 15 วินาที**: ห้าม Reset ตัวนับเป็น 0 ในทันที — วิดีโอต้องเล่นต่อเนื่องได้อย่างราบรื่นจริง ๆ **15 วินาทีขึ้นไป** เท่านั้น ถึงจะยอม Reset ตัวนับกลับเป็น 0
  - **Concurrency Lock**: ใส่ตัวล็อค `isReconnectingRef` ป้องกันไม่ให้มีคำสั่ง retry ตัวอื่นถูกยิงเข้ามาซ้อนขณะกำลังเชื่อมต่อ

### 6. ปัญหาการวิเคราะห์แบบเดาอาการ (Lack of Real-time Logs & Error Details)
* **สิ่งที่เป็นปัญหา**: เวลาเกิดปัญหาบนทีวี ไม่สามารถรู้ได้ว่า ExoPlayer พ่น error อะไรออกมา สตรีมหลุดจากเน็ต หรือหลุดจากชิ้นไฟล์ m3u8 ขาดตอน ต้องคอยคาดเดา
* **วิธีแก้ไขจบปัญหา (Backend JSON Logging + JWT)**:
  - เพิ่มระบบ **Backend JSON Logging**: บันทึก Log ทุก State และ Error ละเอียดจากแอปทีวีลงไฟล์ JSON บนเซิร์ฟเวอร์ แยกตามวันอัตโนมัติ `data/logs/logs-YYYY-MM-DD.json`
  - มีระบบความปลอดภัยผ่าน **JWT Authentication**: ขอ Token ผ่าน API Key เพื่อเข้าถึง Log
  - มี Endpoint บริหารจัดการครบถ้วน:
    - `POST /api/logs`: รับ Log จากทีวีแบบ Non-blocking (Fire-and-forget) ไม่กระทบความลื่นไหล 60fps
    - `GET /api/logs`: อ่าน Log กรองตามวัน (`date`), ระดับ (`level`), แท็ก (`tag`), สถานะ (`state`) พร้อม pagination
    - `GET /api/logs/dates`: ดูรายชื่อไฟล์ Log ทั้งหมดที่มีในระบบ
    - `GET /api/logs/config` & `POST /api/logs/toggle`: ดูสถานะและเปิด/ปิด Flag การเก็บ Log ได้แบบ Real-time
  - บันทึกสถานะทุกขั้นตอนละเอียด: `APP_MOUNTED`, `CHANNEL_COMMITTED`, `PLAYER_READY_TO_PLAY`, `PLAYING_HEARTBEAT`, `PLAYBACK_STABLE_15S`, `PLAYER_STATUS_ERROR`, `AUTO_RECONNECT_SCHEDULED`, `AUTO_RECONNECT_HALTED_MAX_REACHED`

### 7. อาการ: แอปบนทีวีไม่เห็น get list / ไม่มีปุ่มรีโหลดช่องด้วยมือ (Manual Reload & Channel Lifecycle Logging)
* **สิ่งที่เป็นปัญหา**: เปิดแอปมาแล้วรายการช่องไม่ขึ้น หรือหลังบ้านอัปเดตช่องใหม่แล้วในแอปยังเป็นช่องเดิม ไม่มีปุ่มให้กดรีโหลดเอง และบนหน้าดู log ของ Backend ก็ไม่มีข้อมูลการ get list ใดๆ
* **สาเหตุจริงเชิงลึก**:
  1. **ไม่มีการส่ง Log ใน `useChannels.js`**: โค้ดเดิมส่ง Log เฉพาะฝั่ง Player เท่านั้น ไม่ได้สั่งส่ง Log ตอนดึงช่อง (`fetchChannels`) เลย ทำให้บนเซิร์ฟเวอร์ไม่มีประวัติการเชื่อมต่อของรายการช่อง
  2. **ไม่มีปุ่มรีโหลดช่องใน UI**: แอปพึ่งพาการ poll timestamp `/api/health` ทุก 8 วินาทีเท่านั้น หากเน็ตสะดุดชั่วคราว หรือติดแคชในตัวแอป ผู้ใช้จะไม่สามารถสั่งดึงข้อมูลใหม่ได้เลย
  3. **เงื่อนไข Error บังการแสดงผล**: ใน `Sidebar.js` เดิมจะยอมแสดงกล่องแจ้งเตือน error และปุ่มลองใหม่เฉพาะเมื่อ `channels.length === 0` แต่เนื่องจากแอปเรามีช่อง "หน้าหลัก" (`MAIN_CHANNEL`) ยืนพื้นอยู่เสมอ ทำให้ความยาวเป็น 1 ตลอดเวลา กล่องแจ้งเตือนจึงไม่เคยโผล่มาให้เห็น
* **วิธีแก้ไขจบปัญหา**:
  - เพิ่มปุ่ม **`[ 🔄  รีโหลดช่อง ]`** ไว้ด้านบนสุดของ Sidebar:
    - รองรับรีโมตคอนโทรล TV (D-pad) 100%: กดรีโมตขึ้น (D-pad UP) จากช่องแรกเพื่อโฟกัสได้ทันที
    - มีกรอบเรืองแสงสีขาวและพื้นหลัง Accent ชัดเจน

  - **Layer 2 (Fast String Slicing Client Resolver)**: ปรับปรุง `app/src/lib/streamResolver.js` เปลี่ยนจาก Regex เป็น `indexOf` + `slice` ประมวลผลเสร็จใน 0.01ms, เพิ่ม Timeout เป็น 12s, มีระบบ Log ชัดเจน และเมื่อดึง Token สดสำเร็จจะยิงซิงค์ขึ้น Backend ทันที

  1. **Background Polling Loop ทุก 8 วินาที**: ตัวแอปใน `useChannels.js` มีการ Poll ตรวจสอบ `fetchUpdatedAt` ทุกๆ 8 วินาที ซึ่งโค้ดเดิมสั่ง `resolveStreamUrl(c, { forceRefresh: true })` บังคับให้แกะ Signed Token ใหม่จาก ByteArk ทุกรอบ แล้วยิง `POST /api/channels/:id/sync` ขึ้นเซิร์ฟเวอร์

  3. **Player ทำลาย Session วิดีโอที่กำลังเล่นดีอยู่ (`urlChanged` Triggering `player.replace`)**:
     ใน `Player.js` เดิม เมื่อได้รับ Prop `url` ใหม่ที่มี Token สดส่งลงมา มีเงื่อนไข `if (urlChanged || forceReloadRequested)` ซึ่งสั่ง `setLoading(true)` และสั่ง `player.replace({ uri: url })` ทันที

* **วิธีแก้ไขจบปัญหาอย่างถาวร (Industry Streaming Player Best Practice)**:
  - **Uninterrupted Healthy Playback & Silent Token Update (`Player.js`)**:
    - เพิ่ม `currentPlayingChannelIdRef` ระบุช่องที่กำลังเล่นอยู่
    - หากกำลังดูช่องเดิมอยู่ (`!channelChanged && !forceReloadRequested`) และวิดีโอกำลังเล่นได้อย่างราบรื่น (`hasStartedPlayingRef.current === true`), **ไม่อนุญาตให้ขึ้นหน้าจอโหลดดิ้งและห้ามสั่ง `player.replace()` ขัดจังหวะเด็ดขาด**
    - ให้อัปเดต URL ใหม่เก็บไว้ใน `currentUrlRef.current = url` เงียบๆ ในหน่วยความจำ (Silent Ref Update) เพื่อเตรียมไว้เป็น URL สำรองสำหรับการ Reconnect หากเกิด Network Error ในอนาคต
    - อนุญาตให้สั่ง `setLoading(true)` และ `player.replace()` เฉพาะเมื่อผู้ใช้กดสลับช่องจริง (`channelChanged === true`) หรือกดปุ่มรีโหลดช่องด้วยตนเอง (`forceReloadRequested === true`) เท่านั้น
  - **Idempotent Background Polling (`useChannels.js`)**:

    - การ Polling เบื้องหลังทุก 8 วินาทีจะไม่ขอ Token ใหม่ตราบใดที่ Token เดิมยังไม่หมดอายุ (`isUrlExpiring(c.url, 600)` มีอายุเหลือ > 10 นาที)
